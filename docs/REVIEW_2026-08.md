A fresh scan of the whole app: design, UX, feature set, and the two areas

This document does not repeat `docs/IMPROVEMENT_IDEAS.md` (the 60-item
catalog). Where an idea there is still the right answer, it is
referenced as `[IDEAS #n]` and only extended. Everything else here is
new, and grounded in the code as it stands today.

## 1. Command bar — quick-type experience

The bar is genuinely good: order-tolerant grammar, glued-token
splitting, NL tolerance ("6 meters", "2 kom"), ghost text, ↑/↓ recall,
kg/m on size chips, did-you-mean. The following are the gaps I found
against the stated goal — *fewest keystrokes to a trusted number, and
never leave the bar*.

### 1.1 The "Ready" stage wastes the highest-intent moment — **S/M**

`cmdSuggest` (`packages/metal-core/src/command/suggest.ts:279`) returns
a single item once every stage is filled:

```ts
return { hint: "Ready", items: [{ label: "Save calculation", ins: "__save", kind: "save" }] };
```

But "I have a number" is exactly when people want a *variation*, not a
save. Replace the Ready stage with **refine chips** built from the
parsed result:

- `×4` `×10` — quantity steps from the current qty (and from usage habits)
- `12 m` `3 m` — the other common stock lengths for this family
- `HEB 120` `IPE 200` — the sibling profile at comparable section
  (one size up / one size down within `COMMAND_SIZES`)
- `S355` / `304` — the grade the user *didn't* pick, when the family has
  a bimodal habit
- `+ 5% waste` `+ VAT` — inline pricing toggles as tokens
- `Compare` `Save` at the end, not at the start

Each is a one-tap query rewrite, not a new stage. Rank by
`usage-stats.ts` exactly like the other stages already do. This alone
turns the bar from "compose a query" into "explore a decision", which
is the actual job.

### 1.2 Keyboard: no numeric quick-select, no visible key map — **S**

Today: `Tab`/`→` accepts the ghost, `↓` moves focus into the chip row,
`←/→` walks it, `Enter` logs. Missing:

- **`1`–`9` inserts the nth chip** without leaving the input. This is
  the single biggest keystroke saving available and it is ~15 lines in
  the existing keydown handler (`desk-calc-view.tsx:222`).
  Guard: only when the partial token isn't itself numeric — i.e. when
  the current stage is profile/grade, or behind a modifier (`Alt+1..9`)
  for numeric stages.
- **A persistent key-hint strip** under the bar: `↵ log · ⌘S save ·
  ⌘⏎ compare · Tab complete · ↑ recall · ? shortcuts`. The app already
  has all these behaviors; none are discoverable. A 20px muted mono
  strip is the cheapest "premium tool" signal there is.
- **`?` opens a cheat sheet** generated from `COMMAND_ALIASES`
  `[IDEAS #18]`.
- `⌘S` / `⌘⏎` bindings for save / compare so the hand never leaves the
  home row.

### 1.3 `Enter` means two different things — **S**

`onKeyDown` (`command-shell.tsx:1051`, `desk-calc-view.tsx:223`): when
`p.valid` Enter logs to the session tape; otherwise it inserts the first
suggestion. Same key, two mental models, zero labelling. Proposal:

- `Enter` = **accept/advance** always. When the query is valid *and*
  unchanged since the last accept, it logs. When there's a pending
  suggestion, it inserts. That's one rule ("Enter moves me forward"),
  and it matches what users already expect from the ghost text.
- Show the meaning live in the key-hint strip (`↵ insert 6m` →
  `↵ log line`). Changing the label as the meaning changes is the
  premium detail.

### 1.4 The chip row is a scroll on phone and unordered on desktop — **S/M**

Phone (`command-shell.tsx:849`) renders one horizontally scrolling row
with a right fade. For the size stage that's 10+ chips behind a swipe.

- **Two-row wrap on phone** with a "more" affordance instead of a
  scroll: standard sizes are a *grid* mentally, not a queue.
- **Group headers** in the size stage: `Yours` (usage), `Presets`,
  `Standard` — the data is already segmented in `cmdSuggest`, it just
  renders flat.
- **Show the delta on refine chips**: `12 m → 282 kg` under the label,
  same mechanism as the existing `kgm` sub-label. Deciding without
  committing is the whole point.

### 1.5 Returning users always land on the demo query — **S**

`command-shell.tsx:101`: `useState(DEMO_QUERY)`. Great for first visit,
wrong for the 200th. Proposal:

- First visit → demo query (unchanged).
- Returning visit → the newest `quickHistory` entry, pre-selected so a
  single keystroke replaces it, plus the recents as chips.
- Gate on a `ferroscale-onboarded` flag (also unblocks `[IDEAS #26]`).

### 1.6 Suggestion cost per keystroke — **S**

`sizeKgmSub()` (`suggest.ts:77`) calls `cmdParse()` once **per candidate
size, per keystroke**, and `cmdSuggest` itself re-parses the query a
second time after the shell already parsed it (`command-shell.tsx:192`
then `suggest.ts:113`). At the size stage with 12 standard sizes plus
usage sizes, that's 15+ full parses per character.

- Memoize kg/m per `(family, sizeText, gradeId)` — it does not depend on
  the rest of the query. A module-level `Map` is enough.
- Let the shell pass its existing `CommandParseResult` into `cmdSuggest`
  instead of re-parsing.

Nothing is visibly slow today, but "stay fast" is the product promise
and this is the one hot path that scales with catalog size.

### 1.7 Mobile-specific quick-type gaps — **S/M**

- **No history recall on phone.** ↑/↓ exists on medium/wide only. Add a
  one-line recents strip above the keypad (tap = load, long-press =
  delete), which is also where `[IDEAS #16]` ("repeat last, change one
  thing") belongs.
- **Token-wise backspace** on keypad long-press `[IDEAS #38]` — the
  single most requested keypad behavior in tools like this.
- **Haptics** on chip insert / parse issue / save `[IDEAS #34]`. On a
  custom keypad, haptics are what make it feel native rather than
  emulated.
- **The `×` key inserts the character `×`** (`command-keypad.tsx:206`)
  but quantity habit is `x2` — it works because the tokenizer accepts
  both, yet the key produces a token the grammar docs never show. Make
  it insert `x` and render `×`.

### 1.8 Bigger grammar bets (ranked)

These extend the catalog; I'd sequence them in this order:

1. **Multi-item lines** — `hea120 6m x2 + ipe200 4m x3` parses as a
   list, hero shows the sum, tape logs one line per item. This is the
   natural bridge between the bar and projects, and it's the feature
   that makes the bar a *quoting* surface, not a calculator. **M/L**
2. ~~**Reverse/target queries** — `hea120 =500kg` `[IDEAS #6]`. **M**~~
   Shipped in 3.12.0: the token solves for pieces when a length is fixed
   and for length when a quantity is, in weight (`kg`/`t`/`lb`) or money.
3. **`>` command palette** `[IDEAS #10]`, extended: the palette should
   also search **saved entries and projects by name**, so ⌘K is one
   input for "calculate, navigate, recall". That's the premium
   Raycast/Linear feel the app is already reaching for. **M**
4. **Arithmetic tokens** — `6m-50mm`, `x2+3` `[IDEAS #7]`. **S/M**
5. **Paste a cut list** `[IDEAS #8]`. **L**

## 2. Saved cards — the "weird" one

### 2.1 The data model is 3× richer than the UI

`src/hooks/useSaved.ts` implements and exports:

`updateSaved` (rename/notes/tags) · `duplicateSaved` ·
`duplicateSavedMany` · `removeSavedMany` · `addPartToSaved` ·
`appendPartsToSaved` · `removePartFromSaved` · `reorderPartInSaved` ·
`markSavedUsed` · `getSavedCount` · `getSavedEntry`

**None of them is called anywhere in `src/components`.** The
`SavedEntry` type carries `notes`, `tags`, `useCount`, `lastUsedAt`, and
a `parts[]` array (multi-part assemblies), and the UI shows *name,
grade, quantity, date, weight, cost*. The changelog says these features
shipped once (v-history mentions search/sort/duplicate/tags) and the
command-shell rewrite dropped the surface but kept the store.

So "saved could be more functional" is mostly a **UI-only** project:

| Capability | Store | UI | Work |
| --- | --- | --- | --- |
| Rename / notes | ✅ `updateSaved` | ❌ | S |
| Tags + tag filter | ✅ | ❌ | S |
| Sort: newest / most used / recently used | ✅ `useCount`, `lastUsedAt` | ❌ | S |
| Usage count ("used 7×") | ✅ | ❌ (never incremented — `markSavedUsed` is not called on load) | S |
| Duplicate & tweak | ✅ | ❌ | S |
| Multi-part assemblies (BOM) | ✅ `parts[]` | ❌ | M |
| Bulk select → delete / compare / project / CSV | ✅ `removeSavedMany` | ❌ | M |
| Search | — | ❌ | S `[IDEAS #22]` |
| Pin/star | ❌ (one field) | ❌ | S `[IDEAS #20]` |

The multi-part one is the sleeper: a saved entry that holds several
parts *is a bill of materials*. Surfacing it turns "Saved" from a
bookmark list into "my standard assemblies" — railing, gate frame,
mezzanine bay — with a summed weight and cost. That's a genuinely
different product tier, and the storage, sync, and mutation code is
already written and synced.

### 2.2 Why the card looks off, concretely

Current desktop card (`desk-saved-view.tsx:58`):

```
[glyph 40px]  HEA 120 · 6m ×2            [compare] [trash]
              S235 · ×2 · 6 Aug
──────────────────────────────────────────────────────────
TOTAL WEIGHT   141 kg     TOTAL COST   € 169.44
```

Problems, in order of visual weight:

1. **The title repeats the metadata.** `doSave` builds the name as
   `` `${displayName} · ${p.lengthRaw}${p.lengthUnit} ×${p.realQty}` ``
   (`command-shell.tsx:291`), then the meta line under it prints `×2`
   *again* alongside the grade and date. Two lines, one fact, and the
   title truncates on any real profile name.
2. **The identity is a generic glyph.** The app already renders real
   dimensioned cross-sections (`profile-drawing.tsx`, 499 lines, used in
   the result sheet and desktop breakdown). A saved HEA 120 and a saved
   SHS 40×40×3 currently differ by a 22px pictogram. Putting the actual
   section thumbnail on the card is the highest-impact visual change in
   the app and costs nothing new.
3. **Two stat blocks in a footer strip** read as a table cell, not a
   card. There's no hierarchy between them — same size, same weight,
   different colors — so the eye has nothing to land on.
4. **Date as identity.** `6 Aug` sits in the same line as grade and
   quantity, competing with spec data. Provenance belongs in a footer,
   quiet.
5. **Actions are always-on 30px icon squares** with `title` tooltips
   only. Three focusable controls per card, no card-level affordance,
   no hover state beyond a border-color change.
6. **Grid caps at `maxWidth: 960`** on a full-width workspace — on a
   1920px screen, two-thirds of the pane is empty.
7. **The empty state is a bare mono sentence**, while the Compare view
   has a proper icon + title + body empty state
   (`desk-compare-view.tsx:117`). Same app, two conventions.
8. **The mobile version is a completely different object** — a
   `LibraryRow` with a right-aligned two-line number stack
   (`library-sheet.tsx:344`). Nothing carries over from the desktop
   card: not the layout, not the hierarchy, not the actions.

### 2.3 Proposed card

```
┌──────────────────────────────────────────────┐
│  ╭──────╮   HEA 120                      ⌄   │   ← section thumbnail
│  │ ▯▯▯▯ │   6 m × 2 · S235                   │     (real drawing)
│  ╰──────╯                                    │
│                                              │
│   141.2 kg                    € 169.44       │   ← one dominant metric
│   26.7 kg/m · 70.6 kg/pc      @ €1.20/kg     │     (mode-aware), one
│                                              │     secondary + basis
│  ─────────────────────────────────────────   │
│  🔖 used 7× · saved 6 Aug     ↩ ⧉ ⊞ 🗑        │   ← hover-revealed
└──────────────────────────────────────────────┘
```

Rules behind it:

- **Title = spec, not sentence.** `HEA 120` in the display face, the
  spec line (`6 m × 2 · S235`) in mono muted. Names become *optional
  overrides* — when the user renames it to "Gate frame post", the spec
  line still carries the truth.
- **One dominant metric**, chosen by the same weight/price mode the rest
  of the app uses (`weightAsMain` / `modeOverride`). Today the card
  shows both at equal weight and ignores the user's preference entirely.
- **kg/m and kg/piece on the card** — the two numbers people actually
  re-check. Free from the stored result.
- **Pricing provenance** (`@ €1.20/kg`) — see §2.4.
- **Hover reveals actions**; the card itself is a single focusable
  element (`Enter` open, `Delete` remove, `c` compare). Today it's a
  `div` wrapping three tab stops.
- **A `⌄` expander** opens the full breakdown inline (reuse
  `buildBreakdownRows`) and, for multi-part entries, the part list.
- **Same card component on mobile**, one column, actions in a swipe or
  overflow menu — instead of the separate `LibraryRow` implementation.
- **Density toggle**: card grid ↔ compact table (sortable columns:
  profile, kg, €, kg/m, used, date). Power users with 80 saves want the
  table; the grid is for 8.

### 2.4 The trust problem: saved cards show frozen prices

A `SavedEntry` stores the whole `CalculationResult` at save time. Change
the €/kg in Settings tomorrow and every saved card still shows
yesterday's cost, silently, with no indication. Meanwhile clicking the
card restores it via `inputToQuery`, which **omits the price token when
it matches the current default** (`parser.ts:198`) — so the card says
€169.44 and the bar it opens may say something else.

Pick one and make it explicit:

- **Option A (recommended): live re-price, show provenance.** Cards
  compute cost from the current pricing settings and show a quiet
  `@ €1.20/kg` line. If the stored rate differs, show it struck through
  or as a `was €169.44` badge with a "keep original rate" pin.
- **Option B: frozen with a date badge** — `priced 6 Aug` — and a
  "re-price to today" action.

Either is fine; the current *implicit* freeze is the thing that makes
saved entries feel untrustworthy.

### 2.5 Saving itself is lossy

`doSave` (`command-shell.tsx:283`):

```ts
if (!isSaved(p.calc.result)) { … saveCalculation(…) }
pushHistory(query);
showToast(t("toast.saved"));
```

- Saving a duplicate **silently does nothing** but still toasts
  "Saved". The user gets positive feedback for a no-op.
- There is **no saved-state indicator** — the Save button looks
  identical whether or not this exact calculation is already
  bookmarked, and `isSaved` isn't even passed to `CommandDesktop`.
- **No unsave**, no undo (`[IDEAS #19]`), no rename-on-save, no way to
  attach a note at the moment you have the context.

Proposal: make Save a **toggle** with a filled/outlined bookmark icon
driven by `isSaved`; on save show a toast with **Undo** and **Name it**
actions (naming inline in the toast keeps the flow in the bar); on
re-press, unsave with the same undo affordance. And call
`markSavedUsed` when a card is loaded so "used 7×" becomes real and
sorting by "most used" works.

## 3. Design & visual system

### 3.1 The accent color is doing five jobs — **S**

`--accent` (terracotta) currently means: primary action, weight metric,
profile glyphs, active tab, command-line focus glow, and the "save"
chip. When everything is accent, nothing is. Proposal: reserve accent
for **primary action + the weight metric**; move profile glyphs to
`--foreground-secondary`, active-tab to a neutral raised surface (it
already has a shadow doing the work), and let the command-line keep the
glow as its one signature moment.

### 3.2 Numeric typography is inconsistent — **S**

The hero renders in the sans face with `letterSpacing: -2.6/-5`, while
`StatTile`, the tape, and the cards use `font-mono`. Both look
deliberate individually; together the same quantity changes typeface
between the hero and the card two inches below it. Pick a rule and put
it in `globals.css`:

- **Display metrics** (hero): sans, tight tracking, tabular figures.
- **All other numbers**: mono, `font-variant-numeric: tabular-nums`.
- Right-align every column of numbers (the tape already does; the cards
  don't).

### 3.3 Empty and loading states are ad hoc — **S**

Three different conventions: Compare has a proper illustration-style
empty state; Saved and Projects have a bare mono line; the breakdown
rail has an icon + caption. Ship one `EmptyState` atom (icon, title,
body, optional CTA) and use it in all five places. The CTA matters:
Saved's empty state should say *"Press ⌘S on any result"* — teaching a
shortcut at the exact moment of absence.

There is also no skeleton anywhere: saved/projects hydrate from
localStorage in an effect, so the first paint is an empty list that
becomes full. A 150ms skeleton (or an opacity fade-in) removes the
flash.

### 3.4 Motion vocabulary is one-and-a-half effects — **S/M**

`useCountUp` on the hero and a 220ms background transition. Add a small,
consistent set (all behind `prefers-reduced-motion`):

- chip insert → the new token chip scales 0.96→1 with a 120ms fade
- tab switch → 100ms cross-fade of the view body, no layout jump
- tape insert → new row slides in from the top, Σ row counts up
- issue appear → the amber line slides down rather than popping
- save → the bookmark icon fills with a spring, card flies to the tab
  count badge (the "it went somewhere" cue that's missing today)

### 3.5 The medium viewport (640–1023) is the neglected one — **M**

Phone gets the keypad shell, wide gets the dashboard, and 640–1023 gets
a fixed **560px card floating on a background** — no tape, no library
pane, no breakdown, and it's the exact width of an iPad in portrait and
a small laptop window. Define a real mid layout: the desktop shell with
top tabs, single column, tape collapsed to 3 rows, breakdown as an
expandable drawer `[IDEAS #33]`.

### 3.6 Inline styles vs tokens — **M**

`style={{}}` blocks dominate the desktop views (`desk-calc-view.tsx`
alone has ~40). It works, but it makes §3.1–3.4 and any future density
mode a find-and-replace job instead of a token edit. Migrate the
repeated ones (panel, stat, icon-button, label) into shared atoms in
`desk-atoms.tsx` — half of them already have a natural home there
`[IDEAS #32]`.

### 3.7 Small polish items

- Wide-desktop right rail is `maxWidth: 400` and shows an icon +
  caption when invalid — put the **key-hint strip and cheat sheet**
  there instead, so the rail is never dead.
- The tape's Σ row is excellent — the app's best small design moment.
  Extend it: session weight *and* cost *and* line count as a persistent
  "today" strip.
- Saved grid `maxWidth: 960` → remove the cap, let the auto-fill grid
  breathe.
- The brand mark (rounded square inside a rounded square) is the same
  in both light and dark and at every size; a 16px favicon-scale
  variant would help the PWA look intentional on a home screen.

## 4. Feature ideas (new, beyond the catalog)

### 4.1 Per-grade / per-supplier price book — **M** (extends `[IDEAS #44]`)

Pricing today is one global `unitPrice` (`settings-model.ts:143`) plus
an inline `@` override. Stainless 304 costs roughly 4× S235 per kg, so
any user who works across materials has a permanently wrong number
unless they retype `@` every line. A price table keyed by grade (with
optional per-family override) is a small store and changes the app from
"weight calculator with a price field" to "quoting tool". Resolution
order: inline `@` > price book entry > global default.

### 4.2 Margin & sell price — **S/M**

One field (`margin %`) and one breakdown row (`sell price`) turns cost
into an offer. Pairs naturally with 4.1 and with the PDF quote
`[IDEAS #47]`.

### 4.3 Assemblies (surface `parts[]`) — **M**

See §2.1. Saved entries with multiple parts, a summed header, per-part
quantity multiplier, and "add current calculation to this assembly"
from the result actions. The store is done; this is UI + one action.

### 4.4 Session → project in one gesture — **S**

The tape has a running Σ but no way to say "that's a job". A single
"Save session as project" button converts the tape into a project with
all lines. Right now moving 6 lines into a project is 6 × (recall,
open picker, pick).

### 4.5 Shop-floor handoff: QR of the share link — **S**

Desktop shows a QR next to the share action; the phone in someone's
pocket scans it and gets the exact calculation. In a workshop this
beats messaging apps, and the `?q=` plumbing already exists (fix §5.1
first). Tiny QR encoder, no dependency needed at this payload size.

### 4.6 "Explain this number" panel — **S/M**

An expandable line under the hero that spells out the arithmetic:
`26.7 kg/m × 6 m × 2 pieces = 320.4 kg` → `× €1.20/kg` → `+ 5% waste` →
`+ 25% VAT` → `€504.63`, each step from `buildBreakdownRows`. The data
is all there; presenting it as a *chain* rather than a table is what
makes people trust a black box. Also the best possible answer to "why
is this number different from my supplier's".

### 4.7 Recently-deleted / undo everywhere — **S/M** `[IDEAS #19, #27]`

Destructive actions (delete saved, clear tape, clear compare, remove
project calc) are all immediate and irreversible. `clearHistory` wipes a
synced collection with no confirm and no undo.

### 4.8 Two smaller ones

- **Weight tolerance band** `[IDEAS #45]` — nobody else in this category
  shows EN mass tolerance; it's a credibility flex for the EU audience.
- **Section properties** `[IDEAS #39]` — engineers keep a second tab
  open for Ix/Wx today; the dataset rows already carry geometry.

## 5. Correctness / trust issues found

### 5.1 Share links lose the price context — **S**

`buildShareUrl` encodes only `q`. Pricing (unit price, basis, waste,
VAT, currency) lives in the recipient's settings, and `inputToQuery`
deliberately omits the `@` token when it equals *the sender's* default
(`parser.ts:200`). So a link that reads €169.44 on your screen can read
€60 on theirs, with no warning. Either always inline the price token in
share links, or add compact `&p=` pricing params and show a
"link includes sender's pricing" note on hydration.

### 5.2 Saved-card prices vs. restored-query prices can disagree — **S**

Same root cause; see §2.4.

### 5.3 `markSavedUsed` is never called — **S**

`useCount` is always 0 and `lastUsedAt` always undefined, so any future
"most used" sort silently sorts by nothing. Call it in the load path
(`pickInput` in `command-desktop.tsx:52`).

### 5.4 Duplicate-save no-op reports success — **S**

See §2.5.

### 5.5 Usage learning is device-local — **M** `[IDEAS #15]` — ✅ shipped in 3.13.0

`usage-stats.ts` is deliberately local, but the effect is that the
desktop never learns from the phone. For a tool whose premium feel comes
from "it knows my sizes", cross-device habits matter more than the
privacy cost of one more synced (already-encrypted) collection.

Implementation note: habits sync as a **grow-only counter per device**, not
as one shared total. Each device pushes `usage:<deviceId>` holding only what
it learned itself, skips its own record when it comes back on a pull, and the
suggestion source sums every device's tally at read time. A shared total would
double-count on each round trip. With no peers the merge is skipped, so a
single-device user's ordering is bit-for-bit what it was.

## 6. Suggested sequencing

**Sprint A — "Saved becomes an object" (the visible win)** — ✅ shipped in 3.8.0
§2.2 card redesign · §2.1 rename/notes/tags/sort/search/pin · §2.5 save
toggle + undo · §2.4 pricing provenance · §3.3 shared empty state.
Implementation notes: the card, its view-model and the filter/sort logic live
in `src/components/command/saved/` and `src/lib/saved/query.ts`; the drawing
